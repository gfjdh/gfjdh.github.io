2026-11-25 记。一台 Windows 10 22H2 笔记本，WPA2-Enterprise 校园网突然认证失败，排查到最后发现根因跟网络一点关系都没有。

一、症状

11 月 16 日下午开始，笔记本连不上学校 Wi-Fi（CAMPUS-WIFI）。

  • 点连接，转一两秒，提示”无法连接到这个网络”
  • 宿舍 Wi-Fi、手机热点都正常
  • 密码肯定没改过，同一账号在手机上能用

CAMPUS-WIFI 是 WPA2-Enterprise：外层 PEAP，内层 MSCHAPv2，用账号认证，不验证服务器证书。

翻 Microsoft-Windows-WLAN-AutoConfig/Operational，失败事件 12013 的错误码恒为：

注意最后三行——标识、用户、域全是空的。这是后来一切推理的起点。

对照成功事件 12012，这三个字段从来都是有值的：

最后一次成功是 11-16 00:53:18。

二、先把网络层排除干净

在怀疑操作系统之前，得先证明网络本身是好的。这一步做扎实，后面才不会反复回头。

射频和关联

11001 关联成功 是关键——它意味着链路层握手完全正常，AP 认了这台设备，允许它进入认证阶段。

AP 侧加密参数

连续 10 天抓了 114 次 CAMPUS-WIFI 的 RSN IE（无线安全协商信息），114/114 完全一致：

RSN Capabilities = 0x0000 说明这个网络不支持也不要求 PMF（Protected Management Frames），也不是 WPA3。

这排除了两种常见故障：AP 侧参数被改、或者网络升级到了 WPA3 而客户端不兼容。

网卡和驱动

驱动确实有更新版本（3.0.1.1335、3.5.0.1349），但换驱动不解决 0x525——因为 0x525 发生在驱动之上的 OneX 层，网卡驱动根本不参与。

其他常规怀疑

顺手排掉的：

  • MAC 随机化：一开始以为关了，后来发现 RandomMacState 是 1,0,0,0（见第八节新问题 3）
  • 时间不同步：w32tm /query /status 报 0x80070426（服务没启动），但本机时间与真实时间一致，不是这个原因
  • 根证书缺失：Cert:\LocalMachine\Root 有 77 个证书，校园网根证书在里面
  • 多网卡冲突：这台机器只有一块无线网卡
  • 第三方 802.1X 客户端：遍历三个 Uninstall 键匹配 802/Supplicant/AnyConnect/Cisco/H3C/华为/锐捷/深信服/Dr.com 等关键词，没有任何校园网客户端
  • MAC 绑定：AP 侧没有拒绝关联，说明没做 MAC 过滤

结论

网络层完全健康。故障在客户端软件栈更上层。

这个结论很重要——它把排查范围从”网络问题”整个挪到了”Windows 的 802.1X 组件”，后面才有动力去翻 CBS 日志。

三、走过的一堆弯路

这段最值得写，因为每一个”合理怀疑”都被证据否掉了。

弯路 1：以为档案丢了

netsh wlan show profile name="CAMPUS-WIFI" 返回 not found，磁盘上 41 个档案 XML 里也没有它。看起来像是档案被删了。

于是重建档案。这里踩了两个坑：

坑一：命名空间必须是 http:// 不是 https://

坑二：手写 EAP 段几乎必错

我按官方文档手写的 EapHostConfig 段，netsh wlan add profile 直接报 0x80001 根据架构，该配置文件无效。

正确做法是别自己写——Windows 自己就有模板：

这是个 2551 字符的完整 PEAP 档案，直接读出来做字符串替换（改 SSID、关掉服务器证书验证、connectionMode 改 manual）就能用。比自己写靠谱一万倍。

结果：重建成功，仍然 0x525。

弯路 2：以为凭据没写进去

netsh wlan show profile 里有个”配置的凭据”字段，一直显示”否”。看起来像密码没存上。

于是用 WlanSetProfileEapXmlUserData 直接写凭据。这个 API 一直返回 rc=87（ERROR_INVALID_PARAMETER），查了很久才发现真因：

凭据 XML 缺 <Password> 元素就会返回 87。

补上之后 rc=0，凭据确实落盘了——位置是：

不是 HKLM，是 HKCU。1222 字节。

但注意：netsh wlan show profile 的”配置的凭据”字段在有些机器上永远显示”否”，哪怕凭据已经写好了。这个字段不能用来判断。

结果：凭据确认存在，仍然 0x525。

弯路 3：以为 DPAPI 作用域错了

解开 MSMUserData 的 blob，发现 guidMasterKey 指向的是 S-1-5-18\User（机器作用域），而不是用户自己的 Protect 目录。用户上下文解密全部 0x8009000B。

看起来像”Wlansvc 用错了解密作用域”。

但做了对照实验就破功了：拿 6 个普通的 WPA2-PSK 档案（家里路由、手机热点之类，这些都能正常连）做同样测试——结果完全一样，主密钥都在 S-1-5-18\User，用户上下文解密全是 0x8009000B，成功 0/6。

说明 Wlansvc 以 LocalSystem 运行、用机器作用域加密是正常行为，不是故障。

教训：任何”异常现象”都要先做对照，确认它在正常机器上是不是也这样。

弯路 4：以为 EapHost 注册表缺了 PEAP

HKLM\SYSTEM\CurrentControlSet\Services\EapHost\Methods\311 下只有 18、21、23、254、50、55，没有 13（EAP-TLS）、25（PEAP）、26（MSCHAPv2）。

看起来像 PEAP 没注册。

这个怀疑很有说服力，直到我从 WinRE 里挂了一个干净的 Windows 10 的 SYSTEM hive 出来对照：

结果：干净的 Win10，Methods\311 下也只有 21、254、55。

缺 25/26/13 是正常设计——PEAP 和 MSCHAPv2 的实现在 C:\Windows\System32\eapp3hst.dll（Microsoft ThirdPartyEapDispatcher），走的是 legacy EAP 转发层，不在这张表里注册。

这条线彻底作废。

弯路 5：以为系统文件坏了

sfc /scannow 跑 245 秒，只修了一个无关的 OneDrive.lnk。DISM /RestoreHealth 报成功。

修复前后对 10 个关键 EAP 文件算 SHA256，全部未变。

结果：系统文件是好的。

弯路 6：以为权限被剥夺

怀疑某个安全模板把 WlanSvc/EapHost 需要的特权拿掉了。

对比 defltrdsh.inf（RDSH 模板）和 defltbase.inf（普通模板），差异只有 6 处，全跟 802.1X 无关。SeTcbPrivilege 在两个模板里都是空的——服务靠自己的 RequiredPrivileges 拿权限，WlanSvc、EapHost、RasMan 都带。

结果：权限没问题。

弯路 7：以为被改成了多会话/RDPWrap

termsrv.dll 是官方版本（10.0.19041.4522），没有 RDPWrap，没有第三方多会话工具。

结果：没有篡改。

四、真正的转折：读懂 0x525

前面七条弯路走完，我停下来重新看那个错误码。

0x525 = 十进制 1317 = ERROR_NO_SUCH_USER。字面意思是”指定的账户不存在”，很容易理解成”账号或密码错了”。

但这个理解是错的。

在 802.1X 的场景里，0x525 对应的是 OneX 层的 ONEX_UNABLE_TO_IDENTIFY_USER = 0x50001，意思是：

认证模式设成了”用户认证”，但拿不到用户身份。

而”服务器拒绝密码”对应的是完全不同的错误码（0x30a、0x404），并且服务器拒绝时标识字段一定有值——因为服务器得知道你在用哪个账号拒绝你。

这里标识字段是空的，说明请求根本没发出去。

决定性交叉验证

我做了个对照实验：

条件 EAP 类型 凭据 标识字段 结果
有档案 + 有凭据（1222 字节） 25 (PEAP) 有 空 0x525
无档案 + 无凭据 0 无 空 0x525

两种情况，档案、凭据、EAP 类型全都不一样，错误码和空标识一模一样。

→ 0x525 是 OneX 层通用的”拿不到用户身份”，跟凭据对不对没有任何关系。

第二个决定性证据：日志通道静默

这个更狠。Windows 的 EAP 有四个日志通道：

  • Microsoft-Windows-EapHost/Operational
  • Microsoft-Windows-EapMethods-RasTls/Operational
  • Microsoft-Windows-EapMethods-RasChap/Operational
  • Microsoft-Windows-OneX/Operational

查它们的最后写入时间：

全部冻结在故障发生的那一刻。 而 WLAN-AutoConfig 通道在正常滚动记录。

这意味着：故障发生后那 90 多次失败，EAP 方法一次都没被调用过。失败发生在 OneX 层，在 EAP 层之前。

“日志通道没有写入”本身就是证据。 排查时不要只看写了什么，也要看该写而没写的。

六、微软的 KB 文档确认了这件事

搜到 KB2820847，原文 Cause：

When 802.1x authentication mode is configured to user authentication, the supplicant fails to query the user token in the remote desktop session.

Resolution：

we must use computer authentication or “User or computer authentication”

翻译：在远程桌面会话里，802.1X 配成”用户认证”时，请求方拿不到用户令牌。

我的档案正好是 authMode=user，系统正好变成了 RDSH 多会话。完全吻合。

还有 Win32-OpenSSH #2033 佐证，同样的报错配上 Error 0x3F0 in calling WTSQueryUserToken（0x3F0 = ERROR_NO_TOKEN）。

十、方法论总结

这次排查花了很多时间，大部分时间花在错误的怀疑上。回头看，有六条经验值得记下来。

1. 错误码要查”它在这个上下文里是什么意思”

0x525 字面是 ERROR_NO_SUCH_USER，很容易理解成”账号不存在/密码错”。但在 802.1X 里它对应 ONEX_UNABLE_TO_IDENTIFY_USER——“拿不到用户身份”。

同一个数字在不同子系统里含义完全不同。先查这个码在哪个组件产生、那个组件怎么定义它。

2. 空字段是强证据

标识/用户/域三个字段全空，说明请求根本没带身份出去。服务器拒绝你的时候，一定知道你是谁。

3. 日志”没写”也是证据

四个 EAP 通道全部冻结在同一秒，比任何错误信息都说明问题——失败发生在这些组件被调用之前。

排查时要主动去看：这个流程正常跑的话，应该有哪些日志？哪些没出现？

4. 任何异常现象都要做对照

  • 怀疑 DPAPI 作用域错 → 拿 6 个正常档案对照，发现是正常行为
  • 怀疑 Methods\311 缺键 → 挂 WinRE 干净 hive 对照，发现干净系统也这样

没有对照的”异常”很可能是正常现象。

5. 时序能定案

精确到秒的时序把”版本切换”和”故障发作”钉在了一起。反过来，11-15 22:19 到 11-16 02:13 之间还成功连了 4 次，这个反例也很重要——它说明”切版本”和”重启生效”是两个不同的触发点。

6. 修根因会引出新问题，要留后手

切版本修好了 Wi-Fi，但顺手删了 SeServiceLogonRight（搞挂 Docker）、留下了 16 个 pending 包（搞挂 EAP）。

做这类改动前，先把”这个操作会触发哪些组件脚本”想一遍，并且准备好回滚。

十一、还没搞清楚的事

老实说有一个问题我没答案：11-15 22:19 到底是什么触发了版本切换？

CBS 日志只说”正在映射成 ServerRdsh”，没说谁发起的。

有一个可疑的线索：这台机器的 Windows 是第三方 KMS 激活的（kms.example.com:1688），而 ServerRdsh 恰好是批量授权版本。某些激活工具会通过切换版本来获取可激活的 SKU。

但这只是猜测，没有证据。如果是这个原因，那这台机器以后还可能再被切一次——值得留个心。

这些值没有影响任何功能（Wi-Fi 和 Docker 都正常），但严格说系统状态并不完全干净。
