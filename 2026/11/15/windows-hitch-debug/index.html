    楔子：凌晨四点，我坐在一台进不去的电脑前

    我的笔记本是 ASUS ROG Strix G713QY，Ryzen 9 5900HX（8 核 16 线程），32GB 内存，RX 6800M 独显加核显，双 NVMe，Windows 10 企业版 19045。

    它有个毛病，持续了很久：每十几分钟，整台电脑卡住约 1.2 秒，画面、鼠标、声音同时冻住，声音卡出一声失真的爆音。

    驱动全更新过，网上能搜的方法基本试遍了，没用。

    于是我花了十几个小时写工具、抓证据，最后定位到：BIOS 固件缺陷。 刷到新版本之后，卡顿消失了。

    但这个故事真正的高潮不在这里。

    刷完 BIOS 重启之后，我卡在了 Windows 锁屏界面，进不去系统了。

    不是蓝屏，不是启动失败，是更荒诞的一种：锁屏要我设置 PIN，我输微软账号密码，最后一步报错；点跳过，黑屏一下，回到锁屏；网络还断了。重新联网，重新登录，再次报错。

    死循环。

    我从凌晨四点坐到第二天下午，中间试了十几种方法，把 WinRE、注册表、SAM 配置单元、utilman.exe 后门、本地账户、Dism++ 全折腾了一遍，才把电脑救回来。

    而真正的根因，是一个跟密码毫无关系的东西。

    这篇文章分两部分：前半部分讲怎么在一个「什么都不留下」的卡顿上造出证据，后半部分讲我如何把自己锁在电脑外面、又怎么爬出来。

    如果你只想看后者，直接跳到第三部分。

    第一部分：那个每 19 分钟卡一次的问题

    1.1 症状：一卡一卡的，声音还带爆音

    • 不定时地，整台机器卡一下，画面、鼠标、声音同时受影响
    • 声音不是断断续续，而是一声失真的杂音，像拉长的电流声或爆音
    • 每次大约 0.5–2 秒
    • 卡完之后没有任何其他迹象——不蓝屏、不重启、事件日志里什么都没有
    • 跟负载完全无关，空着也卡，满载也卡

    1.2 先排除：不是负载，不是驱动

    排查的第一步不是找原因，是缩小范围。

    事件日志：全空

    System、Application、Kernel-Power 三个日志，在卡顿时刻完全空白。没有 TDR（显卡超时恢复，事件 4101），没有存储错误，没有 ACPI 警告。

    这本身就是一条重要信息：能写事件日志的故障，都是被系统察觉到的故障。这个故障系统根本没察觉。

    声音和画面是同一个事件

    我写了个探针，用静音的 WASAPI 共享模式渲染流，测音频回调的迟到情况：

    卡顿 坏帧数 音频迟到数 关系
    01:23:10 16 16 1:1
    01:25:55 14 14 1:1
    02:01:39 17 15 基本对应

    全时段统计：93 次音频迟到中有 88 次（94.6%）与画面卡顿时间重叠。

    这条排除了所有「单一子系统」的解释：

    • 显卡驱动 TDR 会让画面卡，但声音正常
    • 音频驱动爆音会让声音坏，但画面正常
    • 两个完全独立的子系统被同时阻塞 → 问题在它们共同的底层：系统定时或调度基准

    连监控线程也被冻住

    监控程序里有个每 100ms 采样一次的线程，纯 CPU 计算、不做任何 I/O。全时段它有 153 次迟到超过 150ms，最长 727ms。

    而且每次大卡顿发生时，这个线程恰好在卡顿开始前 41–89ms 停止输出，卡顿结束后才恢复。

    一个纯计算的线程被冻住 = 那一刻整机真的没有在跑任何用户代码。

    1.3 造一把尺子：为什么现成工具全都不行

    任务管理器、LatencyMon 为什么看不见

    因为它们看的是「有多少时间花在 DPC/ISR」。而本机的 DPC/ISR 计数器记账粒度是 15.625ms（1/64 秒，一个时钟节拍）。

    我用 NtQuerySystemInformation(SystemProcessorPerformanceInformation = 8) 以 20ms 间隔连读 core0 的累计 DPC 时间，发现增量永远是 0 或恰好 15625 微秒。

    后果很严重：

    • core0 的 DPC 百分比只会在 14.1% / 28.2% / 42.2% / 56.3% 这些离散值上跳
    • 100ms 采样时峰值虚高 7 倍（33.46% vs 4.67%）
    • timeBeginPeriod(1) 改不了这个粒度

    所以这类工具在本机测不出 1.2 秒的事件——它会被量化得面目全非。

    WPR 跑不起来

    Windows Performance Recorder 是这类问题的标准工具。本机全部失败：

    • 非管理员：wpr -start 报 0xc5585011
    • 提权后：wpr -stop 报 Cannot change thread mode after it is set. Error code: 0x80010106（RPC_E_CHANGED_MODE）
    • logman 报 Access is denied.
    • WPA / xperf 未安装
    • ETW 通道 DxgKrnl / Dwm-Core / Win32k / Audio / DXGI 本机全部不存在

    这条路彻底堵死。

    第一个探针骗了我

    我最初写的是 2ms 高精度定时器探针。跑 60 秒，只测到 1 次 ≥8ms 的停顿。

    看起来 CPU 层毫无问题。

    但我犯了个错误：Windows 会把定时器合并（timer coalescing）。多个进程的定时器会被系统在同一时刻统一释放，所以定时器探针测出来的「同步停顿」大部分是假的，而真实的停顿反而被平滑掉了。

    必须用自旋探针——死循环读 Stopwatch，线程状态永远是 Runnable，永不睡眠，无法被合并。

    换成自旋之后，立刻测到 34 次/分钟、每次 6–60ms 的停顿。

    教训一：在 Windows 上测微秒级停顿，定时器探针是不可信的。必须自旋。

    1.4 真正的证据：core0 的中断上下文被独占

    ISR 占满 1.2 秒

    中断探针以 50ms 分辨率记录每核中断次数与 ISR/DPC 时间。某次卡顿的逐条记录：

    时刻 采样间隔 core0 ISR 占用
    02:20:44.105 87.5 ms 89.3%
    02:20:44.263 148.8 ms 84.0%
    02:20:44.405 72.2 ms 86.5%
    02:20:44.479 73.8 ms 84.7%
    02:20:44.788 70.9 ms 88.2%
    02:20:44.857 68.8 ms 90.8%
    02:20:44.939 83.0 ms 94.1%
    02:20:45.327 132.2 ms 94.6%

    连续 1.2 秒，core0 有 84–95% 的时间在中断上下文里，同期 DPC 几乎为 0。

    不是中断风暴——恰恰相反

    这是整个排查里最反直觉的一条：

    时段 core0 中断速率 全机中断速率
    卡顿窗口（1.4 秒） 1.44 次/ms 15.16 次/ms
    其余全部时间（1433 秒） 2.08 次/ms 22.20 次/ms
    倍数 0.69× 0.68×

    中断次数不但没有暴增，反而降到基线的 0.69 倍。

    这说明不是「太多中断把 CPU 淹了」，而是每一次中断的处理时间被拉长了几十到几百倍——CPU 卡在处理某一个中断里出不来，所以期间新中断反而更少被处理。

    这是驱动在中断处理程序里长时间轮询硬件的典型特征。常见于 ACPI/EC 事务（读电池、读温度、读风扇）或 TPM/PSP 的 SPI Flash 访问。

    十六个核同时停

    用等待型高精度定时器在 core0/1/8/15 四核各绑一个探针，某次冻结的原始记录：

    12 轮连续、四个核同时、时长一致到毫秒级。

    这个模式只能是「所有核心同时被剥夺了 CPU」——单个核的调度延迟不会这样对齐。所以这是一个整机级暂停事件，core0 的 ISR 只是它的触发点或伴随现象。

    一个关键验证：不是「系统时钟冻住了」

    这里有个非常诱人的错误解释。

    所有探针都依赖系统时间。如果 core0 的时钟中断被堵住，KeUpdateSystemTime 跑不了，系统 tick 就停止累加，那么所有基于定时器的探针会一起迟到，看起来就像整机暂停了——而 CPU 其实一直在跑。

    如果这个解释成立，那用户感知到的「卡顿」就只是测量假象。

    必须验证。方法：同时记录三个时间源，在同一个采样循环里逐条对比。

    时间源 来源 是否受系统时钟影响
    QueryPerformanceCounter TSC / HPET 硬件计数器 不受影响
    GetTickCount64() 系统时钟中断累加 受影响
    DateTime.UtcNow 系统时钟中断累加 受影响

    如果某次停顿里 QPC 走了 80ms 而 Tick 只走了 5ms，就是时钟冻结；如果两者同步走了 80ms，就是真实的时间流逝。

    实测：

    25 次停顿事件，全部是 kind=real，CLOCK-FROZEN 为 0 次。 |QPC间隔 − Tick间隔| 最大只有 13ms（采样抖动）。

    系统时钟没有停。QPC 和系统 tick 同步走了 60–85ms，真实的时间确实流逝了。

    这不是测量假象——整机真的停摆了。

    1.5 我犯的两个错

    错误一：我用探针把键鼠干没了

    早期我为了测「所有核心是否同时停」，开了 12 个 HIGH_PRIORITY_CLASS 的自旋线程，占满 12 个逻辑核。

    结果：键盘鼠标完全没反应了几秒钟，直到类似资源管理器重启的现象出现才恢复。

    探针会制造它要测量的现象。 12 个高优先级自旋线程把 16 核里的 12 核吃满，系统连输入线程都调度不上。

    从那以后我的规矩是：

    • 探针绝不用 HIGH_PRIORITY_CLASS
    • 自旋线程最多 1 个，绑 1 个核
    • 分析命令也会干扰测量——我狂扫 16MB 日志时，坏帧率从 0.10% 涨到 0.50%，最长帧从 147.6ms 涨到 301.2ms

    错误二：我把「19.32 分钟精确可预测」说得太满

    最初的数据非常漂亮：

    前 6 次间隔 1158/1170/1150/1145/1187 秒，抖动不到 2%。我据此宣布「固定 19.32 分钟周期，可以预测下一次」。

    后来数据多了，真面目露出来了：

    用全部点做最小二乘拟合，残差最大到 385 秒。单一固定周期模型不成立。

    修正后的说法：周期性但周期会漂移，区间 15–20 分钟。

    教训二：数据量不够的时候，「完美的拟合」往往是错觉。样本少的时候要说得保守。

    第二部分：追 fTPM，追到 BIOS 门口

    2.1 嫌疑排序

    1. 🥇 ASUS ACPI/EC 固件缺陷
    2. 🥈 AMD fTPM（PSP）SPI Flash 访问
    3. 🥉 AMD Crash Defender / Ryzen Master 双版本驱动

    fTPM 那条最诱人：已知 AMD 平台的 fTPM 在访问 SPI ROM 时会阻塞所有核心 1–2 秒，症状正是「画面卡 + 音频爆音」，而且跟 ACPI 问题在 LatencyMon 上难以区分。

    于是决定：关掉 fTPM 验证一下。

    2.2 第一步：BIOS 里找不到

    本机 BIOS 是 G713QY.331（2023-02-24）。进 BIOS，按 F7 切 Advanced Mode，找遍了：

    • Advanced 页只有 9 项：ArmouryCrate Control Interface Support / SVM MODE / ASUS EZ Flash 3 Utility / SMART Settings / Network Stack Configuration / USB Configuration / SATA Configuration / NVMe Configuration / Animation Post Logo Configuration
    • Security 页只有 5 项：Password Description / Administrator Password Status / User Password Status / I/O Interface Security / Secure Boot

    没有 TPM 相关的任何东西。

    我一开始给的指引是「Advanced → AMD fTPM configuration → TPM Device Selection」，这是桌面主板的路径。笔记本 BIOS 根本不用这套。

    2.3 第二步：直接解包 BIOS 镜像看菜单

    与其猜，不如读。

    我把官网下载的 BIOS 更新文件（16,779,264 字节的 ASUS CAP 格式）用 Python 扫了一遍：对每个 zlib 头（78 01/5e/9c/da）尝试 zlib.decompressobj()，对每个 lzma 头（5d 00 00）尝试 lzma.decompress(format=lzma.FORMAT_ALONE)。

    解出 97 个 zlib 流 + 1 个 lzma 流，其中最大那个 10,420,240 字节，就是 UEFI Setup 模块。

    菜单字符串是 UTF-16LE（这就是为什么直接在原始镜像里搜 UTF-16LE 命中 0 处——因为它在压缩流里面）。

    从里面逐字读出来的菜单结构：

    • 一级菜单栏：Main | Advanced | Boot | Security | Save & Exit
    • Trusted Computing 确实存在，在 Advanced 页偏后，紧跟在 Secure Boot / Key Management 之后
    • 进入后：Trusted Computing Settings → TPM State / Security Device Support / Pwd Authentication / TPM Clear / Device Select（TPM 1.2 / 2.0 / Auto）/ PCR Bank 开关
    • 帮助文本：Enable/Disable Security Device. NOTE: Your Computer will reboot during restart in order to change State of the Device.
    • AMD CBS 页也存在：CPU Common Options / DF Common Options / UMC Common Options / NBIO Common Options / FCH Common Options 等
    • 但搜不到 TPM Device Selection、AMD fTPM Configuration、AMD fTPM Switch、PTT、Firmware TPM、Discrete TPM——笔记本走的是通用 AMI 路径，不是桌面主板那套 AMD 专用菜单
    • 也没有 Search / F9 字符串——这版 BIOS 没有 F9 搜索功能，只能手翻

    结论：菜单在固件里，但 BIOS 331 的界面不显示它。

    2.4 第三步：刷 BIOS 335

    官网最新是 G713QY.335（2025-11-07），更新说明写着一句很含糊的话：Improvements to overall system responsiveness（改善整体系统响应性）。

    刷之前做了一堆准备：

    • 挂起 BitLocker（Suspend-BitLocker -MountPoint 'C:' -RebootCount 10）——刷 BIOS 会改 PCR 7，不挂起会跳恢复界面
    • 确认恢复密码保护器在手
    • 找 U 盘。全机只有一块 125GB 的山寨扩容盘（SerialNumber 6661491034209202148，FriendlyName 是空的）
    • 测这块盘靠不靠得住：前 2GB 七个偏移各写 4MB，7/7 成功，但耗时极不均匀（207ms 到 46.4s）
    • 结论：前 2GB 可靠，放 16MB 镜像没问题
    • 格成 FAT32（EZ Flash 只认 FAT32），复制镜像，SHA-256 双向校验一致

    然后进 BIOS，用 EZ Flash 3 刷。刷写本身 2–3 分钟，中间有三个「看似卡住其实正常」的阶段绝不能断电：

    1. 进度条 90% 停十几秒（在写引导块）
    2. 刷完黑屏 1–3 分钟（内存重训，风扇狂转）
    3. 连续自动重启 2–3 次（重建 NVRAM）

    2.5 第四步：刷完了，菜单还是没出现

    SMBIOSBIOSVersion 确认变成 G713QY.335，ReleaseDate 2025/11/7。

    然后进 BIOS 一看：Advanced 页还是那 9 项，Security 页还是那 5 项，Trusted Computing 依然不显示。

    镜像里明明有全部字符串，界面就是不显示——被 suppressif 之类的条件隐藏了，或者这版 BIOS 的 HII 表单根本没注册它。

    教训三：「菜单在 BIOS 镜像里存在」不等于「BIOS 界面会显示它」。从二进制反推菜单路径，要留出「被条件隐藏」的余地。

    fTPM 这条线到此为止。关不掉。

    第三部分：刷完之后，电脑进不去了

    这一部分才是这篇文章真正的核心。

    3.1 死循环的形状

    刷完 BIOS，重启，进入 Windows。

    然后我看到的是：锁屏界面，要求我设置 PIN。

    这本身是预期的——刷 BIOS 改了 PCR 7，TPM 里封装的 PIN 凭证失效，系统要求重新设置。正常流程是：输微软账号密码 → 验证通过 → 设置新 PIN → 进系统。

    实际发生的是：

    1. 输入微软账号和密码
    2. 走到「最后一步，设置 PIN」
    3. 报错
    4. 点「跳过」
    5. 黑屏一下
    6. 回到锁屏
    7. 网络也断了
    8. 重新联网，重新登录
    9. 回到第 1 步

    一个完美的死循环。

    而且注意第 7 步——联网也一起断了。这一开始让我以为是网卡驱动问题，后来才明白这是关键线索。

    3.2 拆解：其实是三个问题叠在一起

    事后复盘，这个死循环是三个独立问题叠加的结果。单独任何一个都有解，叠在一起就无解。

    第一层：PIN 凭证失效

    BIOS 更新 → PCR 7（Secure Boot 状态）变化 → TPM 里封装的 PIN 密钥解不开 → Windows Hello 要求重建 PIN。

    这一层是正常的、预期的，Windows 本来就设计了应对流程。

    第二层：重建 PIN 需要在线验证

    Windows 10/11 在重建 PIN 时，要求微软账户在线验证一次。

    如果验证不了，就退回到「只能用本地缓存的旧凭证登录」。

    这一层也是设计如此。

    第三层：NCSI 认为这台电脑没有网

    这是真正的杀手。

    Windows 判断「我有没有联网」不看你实际能不能上网，而是看一个叫 NCSI（Network Connectivity Status Indicator，网络连接状态指示器） 的探测结果：

    1. 定期向 www.msftconnecttest.com/connecttest.txt 发 HTTP 请求
    2. 期望返回字符串 Microsoft Connect Test
    3. 同时做一次 DNS 探测 dns.msftncsi.com
    4. 拿到预期结果 → 标记「已连接」
    5. 拿不到 → 标记「无 Internet 访问」或「脱机」

    如果这个探测被拦截（防火墙、代理、hosts、安全软件、组策略），Windows 就会一直认为自己离线——即使你实际能上网。

    于是：

    三层叠在一起：PIN 失效 → 需要在线 → 系统认为离线 → 只能用旧密码 → 旧密码不知道。

    而系统的提示是「你的设备处于脱机状态，请使用上次在该设备上使用的密码」——它说得很准确，但它没告诉你「其实你有网，只是我认为你没网」。

    3.6 为什么这么难

    因为系统的提示是「正确但无用」的

    「你的设备处于脱机状态，请使用上次在该设备上使用的密码」——这句话每个字都是对的，但它指向的解决方向是「去找旧密码」，而不是「去修网络状态判断」。

    它告诉你症状，不告诉你病因。

    因为三个问题互相掩护

    • 你以为是 PIN 问题 → 去修 PIN → 修不动，因为要在线验证
    • 你以为是网络问题 → 去修网络 → 修不动，因为实际有网
    • 你以为是账户问题 → 去修账户 → 修不动，因为凭证在 TPM 里

    每个方向都走了一半，都被另一层挡住。而只有把三层拆开单独看，才能找到那个真正的开关。

    因为 AI 帮不上忙

    我全程在跟 AI 对话。它给了很多有用的信息（比如盘符偏移、reg load 绕过 GUI、utilman 后门），但它有个根本局限：

    它按「标准故障」给方案，而我的故障是三个标准故障的叠加。

    每次我说「这个不行」，它就给下一个标准方案。它没法问「你现在系统的 NCSI 状态是什么」——它看不到我的机器。

    AI 擅长的是「已知问题的标准解法」，不擅长的是「未知组合的定位」。 后者需要你自己提出正确的问题。

    而这一次，正确的问题是：「为什么系统认为我离线？」

    回到开头那个卡顿。

    刷完 BIOS、折腾完锁屏之后，我继续用监控工具跑着，准备验证「关 fTPM 有没有用」。

    结果发现：fTPM 没关掉，卡顿却没了。

    刷机后 125 分钟里，真·固件冻结 0 次。

    按刷机前测得的 16.02 分钟周期，这 125 分钟里本该冻结 7.68 次。

    修复来自 BIOS 335 里的其他改动——AGESA 更新、EC 固件更新、ACPI 表修正，具体哪一项不知道，但问题解决了。

    用统计证明它真的消失了

    「感觉不卡了」不算证据。

    判据迭代：宽松判据差点让我得出相反结论

    第一版判据是「平均帧时 ≥55ms 且最长帧 ≥80ms」。

    结果：刷机前 28 次，刷机后 6 次。

    差点写成「BIOS 335 没有解决问题」。

    问题在于：刷机后的 6 次里，大部分是登录/切换用户时的碎噪声——单帧 92.3ms、120.4ms 这种，根本不是固件冻结。

    收紧判据，要求同时满足：

    • 帧数 12 ≤ n ≤ 22（1.2 秒 / 60fps ≈ 17 帧，这是最硬的指纹）
    • 平均帧时 60 ≤ avg ≤ 130ms
    • 最长帧 80 ≤ mx ≤ 400ms
    • 簇跨度 0.6 ≤ span ≤ 2.0 秒
    • mx < 1000ms（排除登录停顿）

    结果：刷机前 17 次，刷机后 1 次（那 1 次是开机后 1.9 分钟的初始化残留）。

    教训四：同一批数据，判据不同结论可以完全相反。分析脚本必须把判据写进注释和报告里。

    里程碑 干净时长 期望冻结 实际 p 值
    刚刷完 107.2 分钟 6.69 次 0 0.12%
    观察中 125.0 分钟 7.68 次 0 0.046%

    顺便分清了两类「卡」

    刷机后还出现过几次「卡」，但性质完全不同：

    时刻 单帧时长 同期事件
    15:37:30.548 3033.9 ms DWM 已注册会话端口 + 火绒 SecurityCenter 状态更新 + AcPowerNotification.exe 崩溃
    15:48:41.880 3002.3 ms Administrator 登录 + 火绒 SecurityCenter

    机制是切换用户 / 登录时 DWM 重建合成会话 + 创建用户配置文件，整个桌面渲染管线停摆 3 秒。这不是固件问题，任何人切换用户都会遇到。

    还有一个反直觉的发现

    某 10 秒里 core0 的 ISR 飙到 42–70%、DPC 飙到 28–100%，但同期帧时完全正常（全部 16.6–17.1ms）。

    反过来，另外几个 dpcMax 高点前后 6 秒内最长帧只有 29–34ms。

    教训五：DPC/ISR 百分比高 ≠ 用户能感觉到卡。判断用户可见卡顿只能看帧探针的实际间隔，不能只看性能计数器。

    第五部分：经验总结

    关于排查方法

    1. 先确认故障真实存在，再找原因。 如果一开始就猜，会一直在错的路上跑。

    2. 探针会制造它要测量的现象。 12 个高优先级自旋线程让键鼠无响应了好几秒。这是最贵的一课。

    3. 现成工具测不出来的时候，要问「为什么测不出来」，而不是「再换一个工具」。 DPC/ISR 记账粒度 15.625ms 这个发现，比任何一次采样都有价值。

    4. 样本少的时候，完美的拟合往往是错觉。 「19.32 分钟精确可预测」在 6 个样本时看起来无懈可击，第 7 个样本就把它打破了。

    5. 判据要写进脚本。 宽松判据会得出完全相反的结论，而且你不会知道。

    关于自救

    1. 系统的错误提示会把你指向错误的解法。 「设备处于脱机状态」让你去修密码，实际要修的是网络状态判断。

    2. 多个故障叠加时，逐个排查会全部失败。 必须先把它们拆开，单独看每一层。

    3. AI 擅长标准解法，不擅长组合定位。 它能给你十个「标准方案」，但定位需要你自己提出正确的问题。

    4. 动手前先想好怎么还原。 utilman 后门用完必须还原，我做完后逐个验证了文件签名。

    关于 Windows 内部

    发现 内容
    DPC/ISR 记账粒度 15.625ms（1/64 秒），NtQuerySystemInformation(8) 增量永远是 0 或 15625
    定时器合并 多进程定时器会被统一释放，定时器探针测「同步停顿」不可信，必须自旋
    QueryThreadCycleTime 返回累计值，两个量必须来自同一对时间点相减，否则算出 1e10 量级的荒谬值
    Process.TotalProcessorTime 本机异常慢（183 进程 1.96–2.95s），改用 NtQuerySystemInformation(5) 一次取全表，4ms
    CallNtPowerInformation(11) 在 Ryzen 上返回标称频率（恒定 3301MHz），不能检测降频
    ETW 通道 DxgKrnl / Dwm-Core / Win32k / Audio / DXGI 在本机全部不存在
    NCSI Windows 判断「有没有网」靠的是探测 www.msftconnecttest.com/connecttest.txt，不是实际连通性
    WinRE 盘符 WinRE 里系统盘通常不是 C:，用 bcdedit | find "osdevice" 确认

    关于 PowerShell（踩了一堆坑）

    1. .ps1 必须 UTF-8 with BOM，否则 PS 5.1 按 cp936 解码，中文全乱码，经常直接语法错误
    2. Write-Host "...{0}" -f $x 会被当成 -ForegroundColor 的缩写，报「无法将值 125 转换为 System.ConsoleColor」。必须整个表达式包进括号：Write-Host ("...{0}" -f $x)
    3. $pid 是只读自动变量
    4. @($genericList) 对 List[object] 抛「参数类型不匹配」，要用 .ToArray()
    5. Add-Type 的 C# 里 catch 不能带未使用的变量名
    6. ConvertTo-Json 生成大 JSON 极慢：343ms / 1.66MB。改用 StringBuilder 手工拼，164ms / 336KB，快 2.1 倍、体积小 4.9 倍
    7. Start-Process -RedirectStandardOutput 的日志是 GBK，不是 UTF-8
    8. .cmd 启动器彻底放弃：cp936 会破坏 UTF-8 中文注释，而且 start 子进程继承 stdout 会导致工具调用挂死。用 .ps1 + .lnk

    后记

    最终的结论

    卡顿：BIOS 331（2023-02-24）有固件缺陷，导致每 15–20 分钟出现一次约 1.2 秒的整机暂停。刷到 BIOS 335（2025-11-07）后消失，p < 0.001。

    机制：core0 陷入长时间中断处理（ISR 84–95% 持续 1.2 秒），同时通过 IPI/广播把其他核心拉进中断上下文，导致所有核心同时无法执行用户代码。中断次数反而降到基线 0.68×——不是中断风暴，是每次中断处理被拉长几十到几百倍。

    锁屏死循环：BIOS 更新导致 PIN 凭证失效，重建 PIN 需要微软账户在线验证，而 NCSI 探测被拦截导致系统误判离线，只允许使用本地缓存的旧密码——而旧密码早已遗忘。

    三层叠加，形成死锁。解法是重置 NCSI 参数。

    两件遗留的事

    • BitLocker：刷机前挂起了，刷完要手动 Resume-BitLocker -MountPoint 'C:'。我做了，ProtectionStatus 已回到 On，TPM 和恢复密码保护器都在。
    • Windows 激活：折腾过程中激活状态丢了（LicenseStatus=5，0xC004F034）。OEM key 是家庭中文版，当前装的是企业版，对不上。暂时不影响使用。

    一句感慨

    这个问题的难点不在「找到原因」，而在「让故障留下证据」。

    卡顿不写日志、不报错、不留痕迹，跟负载无关，跟驱动无关。所有现成的诊断工具都测不出来——不是因为工具不好，而是因为这个故障发生在它们的测量盲区里。

    而锁屏死循环的难点更荒诞：每个提示都是对的，但每个提示都指向错误的方向。

    最后是靠着一堆自己写的小探针，一点一点把「整机停摆 1.2 秒」这个事实钉死的；也是靠着不再相信系统的提示、自己去问「为什么它认为我离线」，才从锁屏里爬出来的。

    排查十几个小时，修复八条命令。 大概这就是这类问题的常态。
